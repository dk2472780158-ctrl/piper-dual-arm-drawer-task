# 全任务：抽抽屉 -> 放方块 -> 合上抽屉 -> 自动归位（π0 的完整任务）

这是把前面两段**合起来**的那一段 ＝ **π0 策略的完整任务**：
拉抽屉 → 把蓝方块放进抽屉 → 合上抽屉 → 回起跑位姿。**2026-10-16 已在真机上整段跑通**：
174 块 / 1738 拍、复位误差 0.0015 rad、跟踪误差 0.0236 rad、抽屉爪咬住 0.0089 m、
末态离起跑位姿 0.0010 ＝ 自动归位走到了。

每一行动作逐字来自语料 today99 / `episode_000041` 第 48..750 拍，只有"最后自动归位"
那一段是补的（演示里机器人没回家）。

客户端就是跑策略的那一份（`../shared/pi0_real_trial_v8.py`）—— 闸门、限速、跟踪校验、
归位、报告、trace 全都不动。本目录自带的本地服务端按序列回答；要跑策略本身，
把服务端换成 3090 上的 π0 策略服务即可（两者共用同一套闸门与限速）。

## 四步（顺序就是执行顺序）

| 步 | 谁动 | 干什么 | 来自 |
|---|---|---|---|
| 1 | 抽屉臂 | 伸手 -> 张爪 -> 咬住抽屉正面左上那个黑色拉环 -> 拉开约 11 cm -> 松爪 | 演示第 48–300 拍 |
| 2 | 方块臂 | 伸过去夹起蓝方块 -> 移到抽屉口 -> 松爪放下 | 演示第 333–600 拍 |
| 3 | 抽屉臂 | 再次前伸/退回，爪全程张着（推不是夹）= 把抽屉合上 | 演示第 640–717 拍 |
| 4 | 两条臂 | **自动归位**：平滑回到复位目标，再保持 1 s | 语料里没有，补的 |

那个圆环拉手是**抽屉自己的把手**，不是另外摆的圈，所以操作步骤里没有"摆布圈"这件事。

上面每一行都是从语料视频里**逐帧看出来的**（不是从动作数值推的）：

- 第 3 步是**推**不是夹：末端压在抽屉正面左半、两片爪张开跨在面板边缘两侧；
  抽屉在 672–681 拍之间一口气滑回关位，之后末端贴着面板到约 710 拍才退开。
- 蓝方块最后在**关上的抽屉里面**（圆盘此时已空）。
- 整段工作区里**没有出现过人手**。

## 无真机测试（四层，都不碰机械臂）

| 模式 | 碰相机 | 碰 CAN | 发指令 | 抓什么 |
|---|---|---|---|---|
| `check` | 不碰 | 不碰 | 不 | 产物指纹、轨迹与旋钮对得上、本地服务能起、链路自检 |
| `cam` | 只开 TCP 流读几帧 | 不碰 | 不 | 相机别名绑定、端口没被占、三路都能出帧 |
| `pose` | 不碰 | **只收反馈**（官方只读路径） | 不 | 实测位姿会不会被客户端使能前的 preload 闸门挡下 |
| `dry-run` | 要（同客户端） | 被动读 | 不 | 客户端整条管线能跑通，`result=dryrun_passed_no_commands` |

`dry-run` 与 `motion` 都会在开跑前**先过一遍 `cam` 那套闸门**：相机坏的话 2 秒就报出来，
而不是等客户端跑到第 8 秒才 `blocked_or_aborted`。

## 开跑前的官方归位（`PI0_RESET`，真机模式默认开）

`motion` 现在是 **`[4c/5] 官方归位` -> `[5/5] 客户端`**：先调上游现成的一键归位
`/home/databall/reset_piper.sh`（立即给两条臂使能、沿受限走廊带回训练起始位姿、自带
±3.20 恢复限位），看到 `PIPER_RESET_SUCCESS` 才往下走；客户端随后照旧把手臂从那里
挪到本段起跑位姿。旋钮：`PI0_RESET=1`（默认）每次都归 / `auto` 先被动读一次位姿、
只在越界时才归 / `0` 跳过（跳过就等于回到旧行为，客户端可能在第 5 步 abort）。

**为什么加**：客户端使能之前有一道 `measured_preload` —— 实测位姿被 clip 到策略动作盒，
任何关节被削掉 > 0.01 rad（夹爪 > 0.001 m）就 abort，**一行动作都发不出去**
（2026-10-16 上午两次 `Raw pose outside preload tolerance` 就是这样）。

**会不会再出现：会。** 两条臂平时坐的位姿正好压在盒子的两条边上（J2 下界 = 0、
J3 上界 = 0），所以任何一点下垂都会顶出去，而容差只有 0.01 rad。断电重启、久放、
搬运之后都可能出现；温度漂移也会。所以默认"每次开跑前先归一次"，而不是等到报错再修。

**为什么不能只看官方那句 nominal 警告**：两个盒子**不是同一个**。官方脚本的 nominal 是
SDK 名义盒（J2 ≥ -0.05、J3 ≤ 0.06、夹爪 ≤ 0.08），客户端 preload 用的是策略动作盒
（J2 ≥ 0、J3 ≤ 0、夹爪 ≤ 0.07，容差 0.01 rad / 0.001 m）。所以有"官方说没事、客户端照样
abort"的组合（J2 = -0.02、夹爪 0.075 之类）。`pose` 模式因此**不是**看官方那句警告，
而是把实测位姿喂给**活客户端那一份** `measured_preload()` 下判决。

### 为什么加这道闸门（2026-10-16 的实例）

断电重启机械臂 → USB 重新枚举 → `/dev/camera_*` 别名重建时指到了**新的 video 节点**
（left 18 / middle 11 / right 4）。而整夜没停的相机推流守护进程手上还捏着**已经不存在的**
老节点（video5/12/19），于是三路流全冻、心跳里的 `sent` 计数不再增长。
两次真机尝试都在客户端第 8 秒 abort（`Camera reader failed: {'top_head': 'Cannot open
MPEG-TS stream'}`），**一行动作都没发出去、电机没使能**。

`check` 那套自检抓不到这个：链路自检是自己造一张假 jpeg 发过去的，从不碰相机。
所以现在把相机单独做成一道闸门，判据与超时全部照抄活客户端（别名↔串号↔USB 父口、
`ss state established` 占用、480x640x3 帧 + 0.6 s 帧龄 + 0.25 s 同步）。
修法就是让推流守护进程按新别名重开相机（`piper_idle_fanout.sh stop` 再 `start`）。

旋钮（都能用环境变量改）：`PI0_PORT` 换端口、`PI0_ARM_TOL` arming 容差、`PI0_REBUILD=1`
强制重建轨迹、`PI0_COUNTDOWN=5` 开跑前倒数（用了它，那一次倒数就发生在**归位**之前，
不会在客户端那里再数一遍）、`PI0_TRACE=0` 不写 trace、`PI0_RESET=0|auto` 见上一节。

跑之前机器上要有的东西：

1. 抽屉**完全关上**，蓝方块在圆盘上（位置与演示一致），两个爪都合着、里面没有东西，
   工作区里没有人手。
2. 硬件锁空着：`flock -n /home/databall/pico_piper_teleop/runtime/hardware.lock true`。
3. 端口 18315 空着（`ss -ltn | grep :18315` 看一眼）。18030/18031/18032 是别的会话的，别碰。

## 它改了什么、没改什么

- **没改**：客户端的**逻辑**一个字节都不动 —— 那份活的原版客户端（含全部闸门、限速、跟踪校验、
  归位、报告、trace，就是真机跑 π0 策略用的那一份）随包放在 `../shared/` 里（与机器上那份活文件同源，只把名字前缀换成了 pi0_），本目录只通过 `--remote-url` 连过来。
  也没碰任何安全阈值、控制参数、模型、数据集、归一化统计。
- **改了**：只在本目录里新增了一份"按轨迹回答"的本地服务，和一份重新构建过的轨迹。
  两条臂都由轨迹供行（cubephase 那份是把抽屉臂钉住的，这份不钉）。

## 为什么不能"原样放"

执行链每拍压步长：客户端 `limited_target`（关节 0.40 rad/s、夹爪 0.030 m/s），
驱动护栏是 `.25*dt+.01` rad / `.006*dt+.001` m。演示的单拍峰值远超两者（拉抽屉段
的 dim4 超 4.0 倍、抽屉爪超 15.6 倍；放方块段更狠，rJ2 超 5.6 倍、rjaw 超 12.4 倍）。
限速器会把"冲过去、到点停住"切成斜坡，**手臂到位与合爪被拉成两条时间线**（实测错位 94 拍）。

做法是**协调时间重参数化**：把整段重采样到一条共享的参照时刻 s，14 个轴永远处在同一个 s，
每拍只把 s 推进到"最慢的那根轴允许的最大值"。相对时序逐字保住；每拍步长进帽 ⇒
客户端限速器变成**空操作**（离线实测实切量 < 1e-12）。

## 离线证过什么、证不了什么

证过的（`test_full.py` 全过 + 启动器第 [2/5] 步的自检）：

- 每拍步长都在帽内，且不撞驱动护栏（有两倍余量）。
- 走一遍真实客户端管线（低通 + 限速）后，限速器一次都没动手。
- 三个录制相位的次序与极值：爪先张到全开再咬住、抽屉臂拉 >1 rad、合抽屉段爪全程张着、
  方块爪"张 -> 合 -> 松"、方块臂 rJ2 跨 >1 rad。
- 归位段末行**逐位等于**复位目标（跑完就坐在起跑位姿上，可以原地再跑）。
- 服务端拒绝"复位目标 ≠ 轨迹起跑状态"的轨迹。

证不了的：**开跑前那次复位、和末尾这次自动归位，走的都是关节空间直线/余弦缓动**，
演示里没有这两条路线，所以离线算不出它们中途会不会碰抽屉。第一次跑把手放急停上。

在机器上实际跑过的（2026-10-16）：

- **`bash run_full.sh motion` → 真机整段跑通**（11:01:17）：**174 块 / 1738 拍**、
  复位误差 **0.0015 rad**、跟踪误差 **0.0236 rad**、抽屉爪咬住 **0.0089 m**、
  抽屉臂拉到 **1.4986**（演示 **1.5014**）、末态离起跑位姿 **0.0010** ＝ 自动归位走到了、
  **0 次 Safety stop**；跑完两条臂仍使能。跑前用户自己做过官方归位。
- `bash run_full.sh cam` → EXIT=0。三路各读到 20 帧、≈23 fps、帧龄 0.02~0.08 s、
  彼此相差 0.061 s；断开后端口立刻空出来。
- `bash run_full.sh dry-run` → EXIT=0，报告 `result = dryrun_passed_no_commands`、
  `chunks=0`、`action_rows_sent=0`、`final_hold.reason="SDK was not initialized"`
  ⇒ **一行命令都没发出去、电机没使能**。它是无真机管线测试，不是真机跑。
  报告：`inference/reports/pi0_full_task_20261016_102722.json`。
